The protocol split · why A2A for some, MCP for others

A2A Agent-to-Agent

Used when the call site needs reasoning. The receiving side has its own LLM and decides how to interpret a free-form brief. The caller sends natural language ("find me a flight from BLR to NRT on Oct 15 for 2 adults, under ₹1.5L total"); the sub-agent extracts the structured arguments, decides which MCP tools to call, picks a recommendation, and replies with prose + structured artifacts.

Stack: a2a-sdk · JSON-RPC 2.0 · Agent Card discovery · task lifecycle (SUBMITTED → WORKING → COMPLETED) · artifact streaming.

MCP Model Context Protocol

Used for deterministic typed operations · no LLM on the receiving side. Tools are functions with typed parameters and return values. The caller knows exactly what it's asking for. No interpretation, no judgment.

Stack: mcp (FastMCP) · streamable-http transport · tools auto-generate JSON schemas from Pydantic types · consumed by LangChain via langchain-mcp-adapters.

The planner uses BOTH protocols because the planner is the one place where this distinction shows up clearly · reasoning sub-agents are A2A (delegate the judgement), deterministic ops are MCP (just do the thing). Sub-agents only need MCP because their reasoning lives in their own LLM; they don't have other agents to delegate to.

Single-agent orchestration patterns

These are the loops that run INSIDE one agent. Even when you build a multi-agent system, every individual sub-agent uses one of these internally. Five worth knowing.

ReAct · Reason + Act
The model alternates "thought, action, observation" in a tight loop until it decides it's done. The default loop in almost every agent framework today.
In our buildEvery sub-agent runs an internal ReAct loop. Planner is one too.
CodeAct · Code as the action
Instead of picking from a fixed list of tools, the model writes arbitrary Python that runs in a sandbox. Sandbox output is the observation. Much more expressive when the action surface spans many APIs or needs composition.
In our buildNot used here · planned for Session 7.
Reflexion · Verbal self-critique
After failing, the agent writes a natural-language critique of WHAT went wrong into persistent memory. The next attempt prepends that critique to the prompt. The agent literally talks to its future self.
In our buildSoft form · critic-agent's review feeds the itinerary-agent's revise call.
Plan-and-Execute
The agent first writes a full multi-step plan, then executes step by step, replanning only if a step fails. Decouples thinking about the WHOLE problem from doing each step. Reduces drift on long-horizon tasks.
In our buildPlanner's 12-step workflow is soft plan-and-execute · the system prompt IS the plan.
ReWOO · Reasoning WithOut Observation
Variant of plan-and-execute · the planner writes the WHOLE tool chain upfront with placeholders, calls execute in parallel, then a solver step fills in the final answer. The LLM is invoked fewer times, so it's cheaper and often faster.
In our buildNot used · the conversational HITL nature of trip planning forces us back into ReAct.

Multi-agent orchestration patterns

These are the topologies for how multiple agents are wired together. Seven worth knowing. Real systems mix three or four of these · the naming matters less than the composition.

1 · Supervisor / Router
One central agent receives the user request and delegates to specialist sub-agents. Sub-agents reply back to the supervisor, which composes the final answer. The user only talks to the supervisor.
In our buildExactly what the planner is · the 6 delegate_to_* tools are A2A calls to specialists.
2 · Swarm / Handoff
No central boss. Agents hand off control to each other directly. Whichever agent is "in charge" can transfer the conversation (triage → billing → refund). Popularised by OpenAI's Swarm · LangGraph supports it via Command(goto=...).
In our buildNot used · we chose centralised supervision for traceability.
3 · Hierarchical · Team-of-teams
Supervisors of supervisors. A top-level orchestrator delegates to mid-level team leads, each with their own sub-agents. Useful when you have more than ten specialists and a flat supervisor would have too many tools to choose from.
In our buildNot used · 6 sub-agents fits cleanly under one supervisor.
4 · Network / Mesh
Every agent can talk to every other agent · fully connected graph. Maximum flexibility, hardest to debug. Rarely a clean fit by design · it usually emerges accidentally and signals you should add a supervisor.
In our buildAvoided · sub-agents never call each other, only the planner.
5 · Pipeline / Sequential
Agents fire in a FIXED order, each consuming the previous one's output (researcher → writer → editor → publisher). Deterministic, no routing decisions. Good for content-generation workflows where steps don't depend on intermediate results.
In our buildNot used · our workflow needs branching (e.g. revise vs proceed after critique).
6 · Debate / Critic-Actor
One agent produces, another critiques, they go back and forth until convergence or a max-rounds cap. Forces explicit adversarial review rather than the producing agent self-judging its own output.
In our buildSoftened · itinerary-agent produces, critic-agent reviews, planner decides whether to revise.
7 · Blackboard
Agents don't talk directly. They read and write to a SHARED state store. Useful when many agents need to converge on a shared world-model without explicit message passing. The store becomes the protocol.
In our buildmcp-trip-state is exactly this · planner + itinerary-agent + todo-agent all read and write to one Redis-backed state.

Plus one orchestration primitive · HITL

Human-in-the-Loop is not strictly a "pattern" · it's a primitive that composes with any of the patterns above. In our build it's the capture_payment interrupt gate · LangGraph's interrupt_before pauses the supervisor BEFORE the irreversible action, the frontend renders an approval modal, and the runtime (not the LLM) enforces the pause.

Deep dive · Supervisor vs Swarm, mechanically

Both patterns look "decentralized" in some sense, but they wire control very differently. Here is the mechanical difference, then the rule for picking between them.

The difference in one sentence:

  • Supervisor is a STAR · the boss is always in the loop, mediating every exchange.
  • Swarm is a CHAIN · control moves laterally and the previous agent drops out.

Concrete consequence in our build: when planner calls delegate_to_flight_agent, the flight-agent runs, returns a result string, the planner gets the floor back. In Swarm, if Triage hands off to Billing, Triage is GONE · Billing talks directly to the user, picks its own next tool, decides on its own whether to hand off to Refund.

How Swarm works mechanically

The core idea · handoff is just another tool call. Each agent has its normal tools plus one or more "handoff tools" that don't do work themselves · they return a signal to the runtime saying "give control to AgentX." In OpenAI's Swarm framework an agent declares handoffs=[billing_agent, refund_agent] and the runtime swaps active agents when the LLM picks one. In LangGraph the equivalent is a tool returning Command(goto="agent_b") to route to that node next turn.

Why Swarm exists · the legitimate cases

Supervisor is the right default for most workflow-shaped problems. But Swarm earns its place when the conversation IS the workflow:

  • Domain conversations like customer support · the user IS talking to the billing specialist when on a billing topic, not to a generalist re-interpreting things on every turn.
  • Token economy · supervisor delegation costs ~2 LLM calls per step (dispatch + interpret). Swarm is 1. A 12-step flow goes from 24 calls to 12 · real money and real latency.
  • Specialist judgment · once Billing has the floor, the billing specialist (not a generalist) decides whether to escalate to Refund. Decision happens with full domain context.
  • No supervisor bottleneck · supervisor sees EVERYTHING and eventually hits context limits. Swarm distributes context across agents.
  • Natural "stay with the current expert" UX · once you're in billing, you should stay there until the topic actually changes. Supervisor forces a round trip on every turn, which feels bureaucratic.

Why Supervisor still wins for our build

Need Supervisor Swarm
Strict ordering (search → hold → check_budget → commit → authorize → capture) Natural · prompt encodes the sequence Scattered · each agent must know "what comes next"
Final coherent synthesis (one trip narrative) Boss has all pieces, writes the summary Last agent in chain may lack context
Bounded policy (never charge without check_budget first) Easy · supervisor enforces Hard · each agent has unilateral handoff authority
Clean audit traces in Phoenix Tree-shaped, easy to read Arbitrary DAG, harder to reason about
Retry / compose ("call A, then B with A's output, retry A if B complains") Trivial · boss orchestrates Awkward · once you hand off you've lost the floor
One-line rule:
Use Swarm when the conversation IS the workflow · drifts across specialists, user talks to whoever is currently in charge, no global ordering.

Use Supervisor when the workflow is BIGGER than the conversation · strict procedure, final synthesis required, policy enforcement, audit matters. Trip planning is this shape · we have a 12-step procedure with hard ordering constraints and money on the line. The 2x LLM cost is worth it.

Real production systems often compose both · Supervisor at the top for the strict workflow, Swarm clusters at the leaves for domain conversations. Imagine a financial advisor app where a top-level Supervisor runs the retirement-planning workflow but swarms over to a Tax cluster when tax questions come up mid-flow, then bubbles back up to the planning workflow.

Sidebar · Swarm and Sagas, same shape different contract

A note for the distributed-systems folks. The Sagas pattern (choreographed flavor · long-running transactions with no central coordinator) looks topologically identical to Swarm · chain of services, each one decides who comes next. Same wire diagram. But the contract underneath is completely different.

Dimension Sagas Swarm
Problem it solves Atomicity of a distributed transaction across services Routing a conversation to the right specialist
Step semantics Each step has a compensating action (cancelHotel undoes bookHotel) Each step is just a conversation turn · no compensation contract
Failure model If step N fails, run compensations for N-1, N-2 backwards If agent can't handle, hand off to someone else · no rollback
Decision logic Deterministic state machine driven by typed events Non-deterministic · LLM decides at runtime where to hand off
State Persistent saga log · resumable weeks after a crash In-memory conversation, usually short-lived
"Done" means All steps committed OR all compensated · two valid terminal states An agent says "I've answered the user," loop ends

Mapping the two communities' vocabularies:

  • Orchestrated Sagas (central saga coordinator) maps to our Supervisor pattern · the planner IS the saga orchestrator deciding the next call from the current state.
  • Choreographed Sagas (event bus, no coordinator) maps topologically to Swarm, but only in the "no central boss" sense · the transaction semantics aren't there.
The real gap surfaced here · agent frameworks mostly lack "compensating actions." In our build, if capture_payment succeeds but then add_calendar_events blows up, we have no formal "refund the payment and release the holds" backout path · the planner LLM has to notice and call refund itself. Sagas spent decades hardening this; agent systems are still figuring it out. Expect saga-aware agent orchestration libraries to appear as agents get more autonomy over money and external state.

When hierarchical earns its place

Mechanically, Hierarchical is just Supervisor recursively applied · no new primitive, just nesting. But three things genuinely change once you stack layers, and they're why you'd actually reach for it.

What forces you there

You don't pick hierarchical because it's prettier · you're forced into it by mundane LLM limitations:

  • Tool count overload · most LLMs measurably degrade at picking the right tool past ~20-30 in the prompt. Clustering into teams of 6-8 specialists drops the active tool count back into the model's sweet spot.
  • Prompt length explosion · with 40 sub-agents your supervisor prompt is 8k tokens just for tool descriptions, paid on every turn. Hierarchical lets each team-lead carry only its team's descriptions.
  • Domain bleed · one supervisor reasoning about legal compliance AND flight routing AND code execution produces mushy decisions because its prompt has to encode every domain's nuance.

What's genuinely new beyond more layers

Three engineering problems emerge that don't exist at one level:

  • State scope · does the leaf agent see the top boss's full conversation or just the team-lead's brief? Usually you SHARD state so leaves only see their slice · less noise, faster reasoning, but you lose cross-team awareness.
  • Result aggregation · does the team-lead return raw sub-agent outputs to the top, or SYNTHESIZE? Synthesis loses detail. Raw passthrough re-creates the tool-count problem one level up. No universally right answer · it's a design call per system.
  • Escalation paths · can a leaf agent skip its team-lead and talk directly to the top? Can teams talk laterally (Team 1 → Team 2 without going through the top)? These are the most interesting design decisions in the whole system.
The meta-insight · hierarchical multi-agent systems are org-chart engineering. All the trade-offs human organizations have wrestled with (middle-management overhead vs flat dysfunction, raw data vs synthesized reports, strict chain-of-command vs cross-team channels) show up in agent systems with the same answers. The corporate-management literature is unexpectedly relevant here.

Rule of thumb: if your supervisor prompt has more than ~15-20 tool descriptions, time to start clustering. Our 6 sub-agents are nowhere near that line · flat supervisor is the right call.

How they compose in our build

Patterns are Lego pieces · the value is in the combination. Through that lens, here is what our system actually is:

Pattern Where it shows up
Supervisor Planner with the 6 delegate_to_* tools · all routing decisions are centralised.
Debate (soft) itinerary-agent ↔ critic-agent round trip, orchestrated by the planner.
Blackboard mcp-trip-state holds the shared budget · spend · itinerary across three callers.
ReAct Every sub-agent's internal loop · model + ToolNode in LangGraph.

The combos matter more than the names. Real systems mix three or four of these. Ours mixes Supervisor + Debate + Blackboard + HITL at the orchestration layer, with ReAct inside every sub-agent. When you describe an architecture, name the combination · not the single pattern · because the interesting design decisions live in HOW the patterns compose, not in any one of them alone.
